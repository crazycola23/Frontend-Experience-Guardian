# 按受影响的应用和构建目标选守卫

先定位改动实际进入的应用包和源码根，再从工单、构建命令或项目配置确认目标。包名、框架名、文件扩展名和目录中碰巧出现的配置文件只提供线索。以同一个“应用包 + 构建目标”为一次检查的范围。

| 已核实的目标 | 守卫报告中的 target / adapter |
| --- | --- |
| 浏览器应用，例如 React、Vue、Nuxt、Next 或静态 HTML | `WEB / BROWSER` |
| uni-app 的 H5 / web 构建 | `WEB / UNIAPP` |
| 微信原生小程序，页面配置与源码属于该小程序根 | `MINIPROGRAM / WX_NATIVE` |
| uni-app 的 mp-weixin 构建 | `MINIPROGRAM / UNIAPP` |

- Monorepo 按应用包或实际消费这个共享组件的入口划分。兄弟应用、依赖包、示例、翻译资源和构建产物里的同名文件不决定当前包的目标。
- uni-app 的 `pages.json` 可服务多个平台。结合构建脚本、平台条件编译和组件的实际引用判断；源项目生成的微信 `app.json` 不改变源代码适配器。
- 同一工单确实涉及多个目标时，各端只检查受影响的操作。同一问题用适用平台标明范围；点名体验评审时每个包与目标各出一份结构相同的报告。
- 普通改动若是两端行为一致的共享文案，核对实际使用的文案键，沿用原交付格式汇报一次。若平台差异会改变结论，先查消费入口和工单，仍有歧义再问一次。
- 专门体验评审或实测需要明确包、目标和适配器。原生微信的 `miniprogramRoot` 指向源码根，应用包路径应结合实际工作区确认。身份仍缺失时可以先说明已有证据及“验收未完成”的原因，只询问能确定归属的项目路径或构建目标；确认之后再出 v1 报告。只缺运行会话且目标已明确时，按报告契约记录必测项。
- 其它构建平台和纯后端改动跳过这两套平台规则。
